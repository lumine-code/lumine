# Large document benchmark

Run `node script/run-large-document-benchmark.js` from the editor repository for a generated smoke case of approximately 0.6 MiB and 300,102 rows. This starts a fresh normal application with an isolated profile, real animation frames, the default editor font, no CI timing overrides, and no session persistence. It does not run through Jasmine. See [large document editing](../docs/large-document-editing.md) for the implementation contracts and supported search behavior.

To measure an existing file, run `node script/run-large-document-benchmark.js --input "PATH" --sparse "RARE PATTERN" --link "../search-panel" --packages search-panel`. `--link` selects current package sources; packages not linked resolve their usual committed dependency pins. The input is never saved or rewritten. The source tree and input must remain unchanged throughout the run. `--plan` validates options and prints a sanitized plan without launching an application. `--help` lists the controls for repetitions, generated rows, search expressions and input spacing.

Only `results.json` is intended for sharing. It records source revisions and streamed source hashes, input byte and decoded-text hashes, runtime versions, package names, font settings, viewport dimensions, counts, timing samples and correctness checks. It excludes input paths, filenames, source text and search expression text. The adjacent isolated profile remains local runtime state and should not be published. No application console log is copied into the report.

The measured phases are cold editor load and first Ctrl+End command; thirty Enter commands at the beginning, middle and end with exact snapshot verification after undo; Select All with exact range verification and selection observers active; Duplicate Lines over that complete selection with exact source/copy verification and restoration of text and selection by undo; sparse and dense search counts through first match and completion; and cancellation after first progress. Uncaught renderer errors and unhandled rejections fail acceptance and are recorded as bounded symbolic codes. Search timing measures the core search session, including its worker and checkpoints, rather than the search-panel widget. Optional packages are active during rendering and input measurements. DOM assertions cover bounded content and scrollbar dimensions, visible glyphs and gutter, the cursor round trip and the IME anchor. Horizontal coordinate checks apply to mounted glyphs: unseen prefixes may still be estimated.

Command durations measure synchronous command dispatch. Input-to-next-RAF latency and raw frame intervals are reported separately, along with scheduling lateness and long-task entries when supported. A RAF callback is not proof that a pixel reached the physical monitor. Open is cold for the new editor and application process; the runner does not flush operating-system disk caches. Input hashing happens after cold navigation, and verification and hashing are excluded from command samples. Repeat complete runs in fresh processes and compare distributions, not a single best sample.

For a quick integration smoke in the ordinary test runner, set `LUMINE_LARGE_DOCUMENT_BENCHMARK_CONFIG` to a JSON object such as `{"inputCount":3,"intervalMs":0,"generatedRows":1000}` and run `npm run test:only -- benchmark/large-document-benchmark-spec.js`. That report identifies `specMode: true` and must not be presented as a production-renderer performance result.

## Stateful correctness workflows

Add `--workflows` to run selection, copy/cut/paste, native ClipboardEvent, Unicode typing, line transforms, search/replacement, read-only, split-view and undo/redo sequences in the normal application. `--rows 1000 --workflows` is a small harness check; use `--input PATH` and the desired `--link` arguments for a real document. Controlled text islands have independent expected results, and edits also verify exact undo/redo and unchanged surrounding source. The workflow checks saving and reloading a separate temporary copy inside the fresh output directory; it never saves the input file.

Clipboard text/image IPC, browser clipboard APIs and native copy/cut entry points are replaced with private endpoints during these workflows. Explicit synthetic ClipboardEvents exercise editor event handlers with a private DataTransfer. This covers editor transport and metadata behavior without asserting interoperability with the user's native clipboard owner. Source and raw input hashes are checked after failures as well as successful runs; workflow hashing occurs before launch too, so these runs are not cold-load performance measurements. Atomic progress snapshots retain attempted actions if a renderer crashes, and host cleanup has a bounded timeout.

The host monitors the owned renderer through both page and browser debugging events, rejecting pending work when that renderer crashes or disappears. Reports retain symbolic failure reasons and bounded allocation-failure hints rather than application logs. Temporary-copy actions record process memory before and after each operation, alongside the renderer heap limit, to make reload allocation regressions observable.

Diagnostic action durations include progress-report I/O and scheduling. Use the separate default performance scenario for latency comparisons. Seeded renderer workflow suites additionally cover giant immutable sources, selection history, marker observer failures, folded Unicode, long-line metrics and copied views; the search-panel package owns its end-to-end search-panel workflow suite.
