# Symbol coordinates during editing

This round removes a synchronous full-document scan from the package fleet's typing path. The symbol registry retained 195778 symbols from the supplied large file, and translated all their points on every character. A diagnostic CPU profile attributed about 500 ms across 60 keystrokes to that translation. The editor's JS buffer was already fast; a consumer of its change events spent most of the command time updating unrelated coordinates.

## Change and VS Code reference

The [VS Code interval tree](https://github.com/microsoft/vscode/blob/main/src/vs/editor/common/model/intervalTree.ts) prunes regions outside an edit and carries displacement through tree deltas. Lumine applies the spatial-pruning idea to its existing symbol representation: a weakly held index groups 128 symbols and records the minimum and maximum row of all navigation and range endpoints. Enclosing ranges are included even when their endpoints do not follow navigation order.

Column-only edits skip blocks outside the changed row. A multiline replacement skips earlier blocks, translates overlapping endpoints with the existing affinity rules, and directly shifts rows in blocks entirely after the replacement. Inside overlapping blocks, numeric row checks reject individual unaffected symbols; this matters when a few enclosing ranges make otherwise distant blocks overlap. Changed block bounds are collected in the same traversal. A transaction containing many column-only changes retains the existing grouped-by-row algorithm. Point and range identities remain shared with tree consumers. The index is prepared cooperatively before publishing a complete symbol bundle, not during the first keystroke; cancellation cannot publish obsolete coordinates.

This is an independent implementation, not a port of VS Code's interval tree. It adds about one block descriptor per 128 symbols without replacing existing Point/Range objects. Multiline edits still visit the affected suffix. Pathological enclosing ranges can make every block overlap, and therefore reduce pruning. Returned symbol arrays and coordinates remain owned by the registry; consumers copy arrays before changing their membership or ordering.

## Fleet measurements

The baseline is the preceding JS model, not native Superstring. The experiment runs before/after/after/before in fresh Electron processes per operation, with 43 explicitly activated packages, the actual SOFiSTiK language server and Outline closed. Each process opens the supplied 8400039-byte, 195789-line file twice, at its middle and 100 rows before EOF. Each case requires the complete 195778-symbol cache before typing 60 characters or Enter keys at 60 Hz, followed immediately by 180 wheel events and six seconds of observation. A 10-second provider timeout allows the full result to complete in both variants.

Concurrent fuzzy-matching and dependency changes appeared during an earlier series, including one process exit before Jasmine started. That series is excluded. Accepted fleet measurements use a separate core checkout at `5460f4e199`, its isolated pinned fuzzy-native dependency, and frozen symbol-package variants. They isolate this coordinate optimization from the parallel fuzzy migration; they do not measure the combined performance of both changes.

Durations below are milliseconds for the entire synchronous editor command, including the active package fleet. Ranges are the two process-level observations per condition, not confidence intervals.

| Character | Near EOF |     10.3–10.8 |      1.2–6.5 |  18.0–18.1 |   7.4–7.8 |

Maximum observed animation-frame intervals during typing fall from approximately 33.4 ms to 16.8 ms for characters, both at the middle and near EOF. Enter frames remain around 16.8 ms in both variants. Candidate scrolling intervals stay at or below approximately 16.8 ms in this series. This does not establish a universal frame budget: the candidate still has an individual Enter command of 33.7 ms. Animation-frame scheduling is not physical presentation latency. Removing recurring coordinate work leaves more room for parsing, rendering and other package activity; it does not remove all first-operation or post-edit spikes.

The final diagnostic profile explains a remaining difference between positions. Across 60 characters, `updateRootLayer` accounts for approximately 265 ms of sampled stack time near EOF, versus about 9 ms at the middle; more syntax work completes in the synchronous edit path near EOF. `WordIndex.find` accounts for about 119–127 ms per typing sequence, largely in cooperative completion tasks. These are accumulated sampled costs, not single pauses, and profiling runs are separate from the accepted latency measurements. They are the next useful targets; symbol translation is no longer a dominant stack.

## Validation and reproduction

The isolated benchmark uses 200000 generated symbols and compares every resulting coordinate. Preparing the index takes 1.8–3.1 ms in the final samples. With long enclosing ranges, Enter near EOF improves from 4.7–7.4 ms to 2.3–2.4 ms; deleting a line there improves from 5.2–7.6 ms to about 2.5 ms. An earlier candidate regressed these cases because block overlap still sent many unrelated points through translation; the per-symbol row checks remove that regression.

Bulk-column results remain less favorable. A transaction with 2000 edits measures 7.8–7.9 ms before and 8.1–8.3 ms after for ordinary ranges, or 8.1–9.1 ms before and 8.2–11.5 ms after for the enclosing-range fixture. That branch retains its previous algorithm; these samples do not establish why its runtime changes. They do establish that this round's gains target repeated single edits, not every batch operation. Both preparation and edit measurements include natural allocation/GC effects; no hard upper bound is claimed.

[Raw samples, source fingerprints and validation](../benchmark/results/symbol-coordinate-performance-2026-10-20.json) record the unfavorable samples too. Package variants are frozen, runs are sequential, and tests/profiles are kept separate from accepted timings. No GC is forced. Private file contents and paths are excluded; unchanged input hashes and matching edited-text/syntax checks are required.

Use [post-edit-refresh-benchmark-spec.js](../benchmark/post-edit-refresh-benchmark-spec.js) with `requireSymbols` set to a symbol-count threshold below the expected count to reproduce the fleet scenario. This readiness condition is necessary: timing with an empty symbol cache would miss the expensive subscriber. Use [symbol-coordinate-benchmark.js](../benchmark/symbol-coordinate-benchmark.js) under Electron's Node mode for isolated coordinate work with generated records. Its cases cover ordinary and long enclosing ranges, start/middle/end edits, row insertion/deletion, and transactions containing 2000 column edits. Final hashes include every navigation point and both range endpoints.
