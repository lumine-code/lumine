# Multicursor input planning performance

Measured on Windows on 15 November 2026 with the actual syntax worker. The comparison isolates the core planner: sequential baseline `c686ffe28ae62bafa9d42071afddf133dc844c04` versus `7a7b7aa5afb44b5700731c2295e1f925d641226f`. Both revisions used the same installed dependencies, current Python/IPython grammar artifacts and benchmark, rather than reconstructing two historical fleet installations. The IPython ownership policy is committed at `570c70338963055a5388033ea404e30ca08b507d` and pinned in the new editor.

The sequential planner changed and reparsed earlier prefixes before deciding later rows. The replacement plans the operation against one immutable context and a compact virtual indentation history. Eligible whitespace input borrows the original native trees without parsing or copying them. When ownership needs verification, one complete candidate forest supplies current language ranges; unambiguously matching owners retain their original typing context and new owners use their freshly parsed trees. No path reparses after each planned prefix. Worker publication still contains final text, indentation and selections in one undo operation. See [syntax analysis ownership](syntax-worker.md) for the API and lifecycle contract.

Each large case used a fresh renderer/profile for each revision, one warmup and two measured Enter operations. The repeated IPython 500 KiB / 128-cursor case used one worker for one warmup and ten measured cycles. All eleven passed. Publication median / maximum was 130.1 / 164.0 ms; command completion median was 146.3 ms and parent settlement median was 363.1 ms. A cycle includes exact output checks, undo, redo, undo and grammar settlement between samples, so this measures repeated operation stability rather than an uninterrupted key burst.

All thirteen processes were accepted: 51 complete cycles, including 38 measured samples. Every cycle checked exact final text and cursor positions, one publication, undo and redo outside the timed operation. All new runs had no failure, recycling or resource-pressure events. Each sequential-baseline process emitted two ordinary recycling requests and no analysis failure. Allocated WASM capacity and live native memory were not measured. Failed or cancelled operations are never counted as fast samples.

The launcher required a clean source revision and a quiet local measurement window. The spec asserted worker registry selection, asynchronous worker mode, the loaded mode's source path and the returned promise. Source and grammar fingerprints were checked before and after every process, with no parser, query-budget or scheduling overrides. Both sides had identical input/output hashes, 27 grammar-file hashes and these SHA-256 fingerprints: benchmark `da3bfb27cbb2faf420a1fd587812109ad7eb7825679f17f2f5f120a6278b2127`, fixture generator `71c9481455845e31a6e9ba82a3d6295145c69829f8c14a8afd43ff3f63a50043`, grammar aggregate `adf5b33a6223cd4c572a7ab9630d3e94fbd4bda874d064feb06cb3ffa8590f8a`.

Reproduce with `npm run benchmark:multicursor-input` after setting `LUMINE_PERF_QUIET_WINDOW=1`; use `--case`, `--samples`, `--warmups`, `--output`, `--package-root` and `--source` / `--revision` as documented in [the launcher](../script/benchmark-multicursor-input.js). It writes per-trial timings, checks and fingerprints to an isolated result directory. The public synthetic fixtures contain no user-file content.

Deterministic coverage includes 1/2/8/32/128/129 cursors, dependent and independent suites, no-op prefixes, hard tabs, retained suffix whitespace, Python/IPython Unicode and CRLF, conservative ownership verification, newly created injections, mixed old/new owners, cancellation, query budgets and typed resource errors. The fast-path gates require zero private parser jobs and zero native tree copies. Quoted IPython and portable root-range cases at 2/32/129 cursors require one completed candidate parse job per layer, including cleanup. Exact renderer tests cover both backends, cursor order, atomic worker publication and undo/redo.
